## 2026-08-07 — SAST gate rename and iteration regularization (issue #11)

**Correlation-id:** `c29a5b1a-f2ce-4f60-ba24-c29fd289cc74`
**Iteration:** v0.15.0

**Previous session:** `4a9e4c58` — [trail](2026-08-05-4a9e4c58.en.md)

### What changed?

Two corrections coming out of the lead developer's review on the Finish
refinement PR.

**1. The `sast` gate became `code-analysis`.** The name promised less than — and
something different from — what the gate delivers: the provisioned quality gate
evaluates violations, duplication **and** security hotspots — maintainability and
reliability, not security alone. SonarSource itself describes the product as a
*static analysis tool*; SAST is a subset of what it does. Three identifiers
renamed together:

| Before | After |
|---|---|
| `gates.sast` (manifest) | `gates.code-analysis` |
| `scripts/check-sast.sh` | `scripts/check-code-analysis.sh` |
| quality gate `prodops-sast` | `prodops-code-analysis` |

**2. v0.15.0 was opened.** The Finish refinement had been running without an
iteration — `iteration-plan.md` read "no active iteration". The work was
decomposed into DS-62, DS-63, and DS-64 under issue #11 and recorded as the
active iteration.

### Why?

**On the rename.** Calling the gate SAST implied that a red result is always a
security finding — when it may be a code smell or duplication. The ambiguity had
a practical cost: the repository uses "SCA" for `gates.dependencies` (Snyk) in
the literal sense of *Software Composition Analysis*, and adopting the acronym
for Sonar as well would make the same term mean two different things in
neighboring gates of the same manifest.

**On the iteration.** ProdOps infrastructure work does belong to an iteration in
this repository's pattern — v0.8.0, v0.11.0, and v0.12.0 are precedents, none of
them touching `api/src`. v0.8.0 states it in its objective: *"this iteration does
not deliver product — it delivers reliability and traceability of the delivery
framework itself"*. There was no reason for the Finish refinement to sit outside
the model.

### Boundary of the rename

"SAST" was **kept** where it describes CodeQL, which is SAST in the strict sense,
and in the explanation of why the gate no longer carries that name. The three
tools are now explicitly distinguished in the skills:

- `code-analysis` (Sonar, local) — analyzes the source code
- `dependencies` (Snyk, SCA) — analyzes third-party libraries
- CodeQL (SAST, remote in CI) — analyzes the source code for vulnerabilities

### What changed?

**1. Rebase onto `master`.** `master` had moved 21 commits ahead of the branch
point. Zero file overlap between the two sides — the branch's 17 commits
replayed with no conflict.

**2. Orphan trails resolved.** This was the only open review comment. The 7

**3. Root cause identified.** `templates/delivery/context-capsule.md` declared

regeneration (`((COUNT++))` returning 1 under `set -e`; SIGPIPE from

third was worse: the script assumed one skill = one file and never materialized
`steps/`, leaving dangling links in `finish`, `hack`, `sync` and `upstream` for
all three players — invisible because `--check` only inspected the top-level
`SKILL.md`.

deleted in `754873c5`.

### Why?

The Dev's instruction was "change freely to keep consistency", with the layer
rationale from `contributor-philosophy.md`. Applying that rationale led to the
**opposite** of the suggested change: moving `sessions/` into the iteration
folder would violate Rule 1 and the reproducible ideal — a session is addressed
by its ID, may span iterations, and its location must not depend on mutable
delivery state.

## 2026-08-10 — Dev review: CI-bypassing push and gate ownership (issue #11)

**Correlation-id:** `c29a5b1a-f2ce-4f60-ba24-c29fd289cc74`
**Iteration:** v0.15.0
**DS:** DS-62 (finish-substeps) · DS-63 (finish-quality-gates) · DS-64 (commit-workflow-rules) · DS-66 (skill-materialization-fix)
**Branch:** `refine/11-finish-v2` (derived from `master`)
**Issue:** #11
**Commit:** `33a3de6d`

### What changed?

Second review by the lead Dev on the Finish refinement — 6 findings. Three were
real defects, two did not reproduce, and one was right about the risk but wrong
about the cause.

**1. Push straight into the target branch (CRITICAL).** Step 7 instructed
`git push origin HEAD:<origin-branch>`, writing directly into the PR's target
branch without a single CI check running — and `request` would then open a PR
already merged or empty. Fixed to `git push origin HEAD`. The ambiguous term
"origin branch" had propagated into `request`'s preconditions: **4 sites fixed**,
in both languages.

**2. Gate ownership consolidated into `validate`.** `request` was executing
`check-coverage-threshold.sh`, `check-dependencies.sh` and
`check-code-analysis.sh` — violating its boundary ("nothing but opening the PR")
and consuming a coverage XML that could belong to another session. All three now
run in `validate`, which reports the verdicts; `request` only reads them.
`gates.coverage` now runs immediately after acceptance — the only point in the
flow where the XML is fresh by construction.

**3. `validate` stopped dirtying the tree it requires clean.** The step told the
agent to run `npm run format` (`prettier --write`) and `npm run lint` (`--fix`),
both mutating, against its own Guardrail "do not write code". Replaced with
`npx prettier --check` and `npx eslint` without `--fix` — the latter identical to
`pr-gates.yml`'s `lint` job. Plus a clean-tree guard for the silent divergence
caused by Hack's `--fix`.

**4. The two `commit-msg.sh` findings did not reproduce.** The review claimed
`MSG=$(cat "$1")` made the hook reject any commit with a body or trailer. The
script has read `head -1` since `2c4168bb`. Verified by execution — a commit with
a period-ending body and `Co-Authored-By:` is accepted — and by **mutation**:
injecting the `cat` makes exactly 4 cases fail. The script was left untouched.

**5. `commit-msg` regression suite.** `test-commit-msg.sh`, 16 cases through a
real `git commit`, plus `check-commit-msg-suite.sh`, which runs only when the diff
touches the commit-workflow scripts. The wrapper exists because the inline form
(`git diff | grep`) **fails open**: unresolvable base → `git diff` aborts → `grep`
does not match → suite silently skipped. The wrapper treats an undeterminable base
as "run it anyway".

**6. Materialization gate in CI.** `materialize-skills.sh --check` was added to the
`prodops_consistency` job. The push fix existed only in `prodops/skills/` — the
three players were reading stale copies, leaving the CRITICAL fix **inert** for
every agent. It is the failure that only surfaces when another player runs the
skill.

### Why?

The common thread across the three real defects is the same: **a contract edited
on one side only**. The push refspec was fixed at the source but not in the
players; `request` consumed an artifact nobody guaranteed fresh; `validate`
required a clean tree while instructing the agent to dirty it. The materialization
gate attacks the whole class.

On the two false findings, the decision was **not to "fix" them**. Changing a
correct guard to satisfy a review would have broken the hook — and since every
commit in this flow carries `Co-Authored-By:`, the review's premise refuted
itself: had the defect existed, no commit in this repository would have been
possible.

The manifest's `gates.lint` was **kept** as `cd api && npm run lint`: Hack needs
`--fix` (it is a mutating phase) and Finish/CI need the inspecting form. Both
satisfy `expect: exit0` — the divergence is intentional, not a defect.
