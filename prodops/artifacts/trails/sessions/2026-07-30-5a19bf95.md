## 2026-07-30 — DS-38: Criar Invoice PIX — Hack TDD

### Summary

TDD cycle Red → Green → Yellow para DS-38 (POST /invoices com billingType PIX via Asaas).
O ciclo endereçou a lacuna nos cenários BDD 5 e 6 (falha transiente e falha de validação do provedor),
adicionando testes unitários PIX e corrigindo o comportamento de status para falhas transientes.

### Scope

- `api/src/modules/invoices/services/invoice.service.ts` — implementação
- `api/src/modules/invoices/services/invoice.service.spec.ts` — testes unitários

### RED Phase

**Comando:** `npx jest --testPathPatterns invoice.service.spec`

**Teste que falhou:**
```
InvoiceService — Falhas de provedor PIX (DS-38)
  Cenário 5 PIX: Falha transiente ao criar cobrança PIX no provedor
    ✕ marca invoice como PROVIDER_PENDING em falha transiente (PIX)

Expected: (invoice, 'PROVIDER_PENDING', { failureReason: '...' })
Received: (invoice, 'FAILED', { failureReason: 'Request failed with status code 503' })
```

**Razão do RED:** A OBC define "Falha transiente (timeout, 5xx) gera estado `PROVIDER_PENDING`",
mas o catch block em `createInvoice` sempre atualizava para `FAILED` independentemente do tipo de erro.

### GREEN Phase

**Mudança implementada em `invoice.service.ts`:**

Adicionado uso de `isRetryableProviderError()` (método já existente) para determinar o status final:
- Erros retryable (timeout, 5xx, ECONNRESET, ETIMEDOUT) → `PROVIDER_PENDING`
- Erros não-retryable (validação, contract violation) → `FAILED`

  ✓ a mensagem de erro não expõe bankSlipUrl nem identificationField
InvoiceService — Falhas de provedor PIX (DS-38)
  ✓ marca invoice como PROVIDER_PENDING em falha transiente (PIX)
