## 2026-08-01 — payment-confirmation (DS-39, work-item #106)

### Summary

TDD cycle para implementar a confirmação de pagamento por webhook (DS-39).

Lacuna identificada: `receiveProviderPayment()` no `InvoiceService` não emitia o evento canônico `payment.received` exigido pelo OBC (`payment.received` — Liquidação financeira confirmada — para conciliação). A implementação já persistia o evento bruto e atualizava a invoice para `RECEIVED`, mas não publicava o evento canônico para consumo downstream.

**Mudança:** adição de `this.eventEmitter.emit('payment.received', {...})` em `receiveProviderPayment()`.

## 2026-08-01 — api-token-validation (work-item #107, v0.6.0)

### Summary

TDD cycle para validação de acesso à Payments API por token (BDD: `prodops/artifacts/bdd/api-token-validation.feature`).

A implementação (`AuthModule`) já estava completa no master: `ApiTokenGuard`, `ApiTokenService`, `TokenRepository` e `AdminTokenController`. A feature branch `feat/107-api-token-validation` foi criada a partir do master sem commits adicionais.

Todos os 7 cenários BDD cobertos:
1. Token válido — requisição autorizada e evento `api.token.validated` emitido
2. Sem token — 401 com reason `token_missing`
3. Token inválido — 401 com reason `token_invalid`
4. Token revogado — 401 com reason `token_revoked`
5. `API_TOKEN_LOCAL` aceito como escape hatch de dev (tenant `local`, tokenId `local-dev`)
6. Rota `/webhook/payments` isenta do guard `X-Api-Token`
7. Token não aparece em logs nem no body da resposta 401
